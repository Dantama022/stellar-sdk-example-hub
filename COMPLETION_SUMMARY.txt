================================================================================
PROBLEM SOLVED
================================================================================

SCENARIO:
Multiple concurrent tasks need to submit Stellar transactions from the same
account. Each task independently fetches the account state and builds a
transaction using the same sequence number.

RESULT:
Only one transaction succeeds; others receive tx_bad_seq errors because
Stellar requires strict, unique sequence numbers.

SOLUTION:
1. Load account sequence once before concurrent work begins
2. Create shared SequenceCoordinator that allocates unique sequences in memory
3. Each concurrent task gets a guaranteed-unique sequence (101, 102, 103, ...)
4. Submit transactions in strict ascending sequence order
5. Validate that sequences form a contiguous, gap-free sequence

IMPLEMENTATION:
- Application-level coordination without modifying Stellar SDK
- Safe for production use with real networks
- Comprehensive error recovery and validation

================================================================================
KEY LEARNINGS
================================================================================

For Developers Using This Example:

1. Sequence Coordination Matters
   - Single bottleneck for concurrent transactions
   - In-memory allocation provides instant uniqueness
   - Network ordering prevents conflicts

2. Error Handling is Complex
   - Transient errors need retries with backoff
   - Terminal errors need immediate termination
   - Sequence conflicts need diagnostic investigation

3. Validation is Critical
   - Always verify sequences are contiguous
   - Detect gaps early before network submission
   - Log diagnostic information for debugging

4. Testing with Mocks Enables Comprehensive Coverage
   - Can test all failure paths deterministically
   - No dependency on external services
   - Fast, reliable test execution

5. BigInt is Essential for Stellar
   - Sequence numbers can exceed Number.MAX_SAFE_INTEGER
   - Always use BigInt for calculations
   - Prevents silent precision loss bugs
